## 什么时候用

中后台接口通常带统一信封（`{ code, message, data }`）、需要携带登录令牌，并期望成功 / 失败都有一致的提示。API 层把这些横切逻辑收进每个端点的客户端，页面只关心业务数据：

- 页面取数（列表、详情）用 [`useApiFetch`](/docs/api/use-api-fetch) 系列，它是 Nuxt `useFetch` 的薄封装。
- 提交、删除等命令式调用用 [`$api`](/docs/api/api-plugin)。
- 需要进度的文件传输用 [`useUploadWithProgress` / `useDownloadWithProgress`](/docs/api/upload-download)。
- SSE 与 AI 对话用 [`useApiStream` / `createChatTransport`](/docs/api/stream)。

它们走同一条请求管线，端点、认证、业务码校验、错误模型与 [Hooks](/docs/api/hooks) 完全一致。

::warning
API 层依赖 Nuxt 服务端运行时与插件系统，**仅 Nuxt 模式可用**。通过 `@movk/nuxt/vite` 在纯 Vue + Vite 项目中使用时，不提供 `$api`、`useApiFetch*`、上传下载与流式请求。
::

## 最小示例

模块默认启用 API 层，`default` 端点的 `baseURL` 为 `/api`。在 `nuxt.config.ts` 中按需覆盖：

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@movk/nuxt'],
  movk: {
    api: {
      endpoints: {
        default: { baseURL: '/api' }
      }
    }
  }
})
```

后端返回 `{ code: 200, message: 'ok', data: { id: 1, name: 'Alice' } }` 时，泛型 `T` 直接声明 `data` 的类型：

```vue
<script setup lang="ts">
interface User {
  id: number
  name: string
}

const { data, status, error } = await useApiFetch<User>('/user')
// data.value => { id: 1, name: 'Alice' }
</script>
```

## 选择合适的工具

| 场景 | 工具 | 说明 |
| --- | --- | --- |
| 首屏核心数据 | `useApiFetch` | SSR 取数，阻塞导航直到数据就绪 |
| 次要 / 非首屏数据 | `useLazyApiFetch` | SSR 取数，不阻塞导航 |
| 非 SEO 敏感数据 | `useClientApiFetch` | 跳过 SSR，客户端水合后自动请求 |
| 事件处理器、聚合请求 | `$api` | 命令式调用，返回解包后的数据 |
| 带进度的上传 / 下载 | `useUploadWithProgress` / `useDownloadWithProgress` | 仅客户端，可中止 |
| SSE、AI 对话 | `useApiStream` / `createChatTransport` | 仅客户端，可中止 |

`useApiFetch` 继承 Nuxt `useFetch` 的 `server`、`lazy`、`immediate` 等选项，语义与 Nuxt 一致，见 [Nuxt 数据获取](https://nuxt.com/docs/4.x/getting-started/data-fetching)。

## 请求管线

`api.factory` 插件为每个端点创建一个包装 ofetch 的客户端并按名称缓存。每次调用时内置钩子排在用户钩子之前组合执行，用户传入的 `onRequest` / `onResponse` 不会覆盖内置逻辑：

```text
movk.api 配置（全局 + 端点合并）
    |
    v
端点客户端
├── onRequest   认证头注入 -> debug 日志 -> movk:api:request
├── onResponse  流内 JSON 还原 -> 业务码校验 -> 解包 -> movk:api:response -> 成功 Toast
└── 出口        归一为 ApiError -> 401 处理 -> movk:api:error -> 错误 Toast（重试结束后只上报一次）
    |
    v
$api / useApiFetch 系列 / 上传（XHR 适配器）/ 下载（$api.raw）/ 流式（$api.stream）
```

核心规则：

- **业务码校验**：响应 `code` 不在 `successCodes`（默认 `[200, 0, '200', '0']`）内时抛出业务错误。
- **解包**：按 `dataKey`（默认 `data`）取出业务数据，泛型 `T` 即业务数据类型。
- **端点级策略**：直接返回数组或裸对象的端点，在端点 `response` 上关闭 `businessCheck` / `unwrap`，见 [响应策略](/docs/api/api-plugin#响应策略)。
- **统一错误**：业务码、HTTP 4xx/5xx、网络中断、超时统一为 `ApiError`，按 `error.data.kind` 区分，见 [错误模型](/docs/api/api-plugin#错误模型)。
- **401 处理**：HTTP 401 或业务码 401 默认清除会话并跳转登录页，可通过 [`movk:api:unauthorized`](/docs/api/hooks#movkapiunauthorized) 接管。
- **流式短路**：SSE 与二进制响应不进业务码校验与解包，由下载、流式请求自行消费；`application/json` 响应即使按流读取也会先还原为对象再校验。

完整配置项见 [配置 - API](/docs/getting-started/configuration#api)。

## v1 升级说明

v2 把响应处理收敛到每个端点一个客户端，以下写法需要调整：

| 变更 | v1 | v2 |
| --- | --- | --- |
| 请求级开关改为正向命名 | `skipBusinessCheck: true` / `skipUnwrap: true` | `businessCheck: false` / `unwrap: false` |
| `$api` 请求级选项不再包在 `context` 中 | `$api(url, { context: { toast: false } })` | `$api(url, { toast: false })` |
| 裸资源端点在端点上声明 | 每个请求传两个 skip 开关 | `endpoints.x.response: { businessCheck: false, unwrap: false }` |
| 所有失败统一为 `ApiError` | `error.isBusinessError`、`error.response`；HTTP / 网络错误为 `FetchError` | `error.data.kind`、`error.data.response`；HTTP、网络、超时同样是 `ApiError` |
| `movk:api:error` 签名与触发次数 | `(context)`，GET 5xx 重试时触发两次，网络错误不触发 | `(context, error)`，重试结束后触发一次，网络错误与超时同样触发 |
| 上传超时选项改名 | `timeoutMs` | `timeout` |
| 上传 / 下载请求头 | 用户 `headers` 覆盖认证头，忽略端点 `publicHeaders` | 注入端点 `publicHeaders`；启用认证时认证头最后写入、优先级最高 |
| 上传 / 下载关闭校验后的返回 | `skipBusinessCheck` 返回原始响应体 | `businessCheck: false` 仍按 `dataKey` 解包，需要原始响应体时再传 `unwrap: false` |

v1 中依赖用户 `onResponse` 覆盖内置拦截器来绕过解包的写法，需改为 `unwrap: false`。
