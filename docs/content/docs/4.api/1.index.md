## Nuxt 数据获取基础

Nuxt 提供三种数据获取方式，理解它们的区别有助于选择正确的 Movk Nuxt 封装。

- [`$fetch`](https://nuxt.com/docs/4.x/api/utils/dollarfetch) ：底层 HTTP 客户端，基于 [ofetch](https://github.com/unjs/ofetch)，在服务端和客户端均可运行。

  ```ts
  // 用户点击时调用 -- 适合 $fetch
  async function handleSubmit() {
    const result = await $fetch('/api/login', {
      method: 'POST',
      body: { username, password }
    })
  }
  ```

- [`useFetch`](https://nuxt.com/docs/4.x/api/composables/use-fetch)：`useAsyncData` + `$fetch` 的语法糖封装

  ```ts
  // 页面加载时获取数据 -- 适合 useFetch
  const { data: posts, status, error } = await useFetch('/api/posts')
  ```

- [`useAsyncData`](https://nuxt.com/docs/4.x/api/composables/use-async-data)：最灵活的数据获取 composable。

  ```ts
  // 聚合多个接口 -- 适合 useAsyncData
  const { data } = await useAsyncData('dashboard', async () => {
    const [users, stats] = await Promise.all([
      $fetch('/api/users'),
      $fetch('/api/stats')
    ])
    return { users, stats }
  })
  ```

## 关键参数详解

`useFetch`（以及 `useApiFetch`）的三个核心参数决定了请求的执行时机和行为。

### `server`

控制是否在服务端执行数据获取。**默认 `true`**。

**行为对比：**

- `server: true`（默认）-- SSR 时在服务端执行请求，数据通过 payload 传到客户端，客户端不再重复请求
- `server: false` -- 仅在客户端执行。首次加载时数据在 hydration 完成后才开始获取，`data` 初始为 `null`

**使用场景：**

- `server: true` -- SEO 相关数据、首屏需要展示的内容
- `server: false` -- 非 SEO 敏感数据（用户评论、个性化推荐、统计数据），减轻服务端负担

```ts
// 文章列表需要 SEO -- server: true（默认）
const { data: posts } = await useApiFetch<Post[]>('/posts')

// 评论数据不需要 SSR -- server: false
const { data: comments } = useApiFetch('/comments', {
  server: false,
  lazy: true,
})
```

::note
`server: false` 通常与 `lazy: true` 搭配使用，这正是 [`useClientApiFetch`](/docs/api/use-api-fetch#useclientapifetch) 的预设行为。
::

### `lazy`

控制是否阻塞客户端导航。**默认 `false`**。

**行为对比：**

- `lazy: false`（默认）-- 通过 Vue Suspense 阻塞导航，等数据返回后才完成路由切换。用户看不到 loading 状态
- `lazy: true` -- 不阻塞导航，页面立即显示，数据在后台获取。需要手动处理 loading 状态

**使用场景：**

- `lazy: false` -- 页面核心数据，没有数据页面无法正常渲染
- `lazy: true` -- 次要数据、非首屏数据、可以先展示骨架屏的场景

```ts
// 核心数据 -- 阻塞导航等待数据（默认）
const { data: article } = await useApiFetch<Article>(`/articles/${id}`)

// 次要数据 -- 不阻塞导航，后台加载
const { data: related, status } = useLazyApiFetch<Article[]>(
  `/articles/${id}/related`
)
```

```vue
<template>
  <!-- 使用 lazy 时需要处理 loading 状态 -->
  <div v-if="status === 'pending'">
    <USkeleton class="h-20 w-full" />
  </div>
  <RelatedArticles v-else :articles="related" />
</template>
```

::note
SSR 阶段 `lazy` 的行为与非 lazy 基本一致（都会等待数据返回），差异主要体现在**客户端导航**时。
::

### `immediate`

控制是否在 composable 初始化时立即执行请求。**默认 `true`**。

**行为对比：**

- `immediate: true`（默认）-- 创建时立即触发请求
- `immediate: false` -- 不自动请求，`status` 为 `idle`，需手动调用 `execute()` 触发

**使用场景：**

- `immediate: true` -- 页面加载就需要的数据
- `immediate: false` -- 需要等待用户操作后才触发的请求

```ts
// 预定义表单提交请求，不自动执行
const { data, execute, status, error } = useApiFetch('/login', {
  method: 'POST',
  body: credentials,
  immediate: false,
  lazy: true,
})

// 用户点击登录按钮时手动触发
async function handleLogin() {
  await execute()
  if (!error.value) {
    navigateTo('/dashboard')
  }
}
```

::tip
`immediate: false` 常与 `lazy: true` 搭配使用。如果只设 `immediate: false` 而不设 `lazy: true`，Suspense 仍会等待（虽然请求从未发出），可能导致页面悬挂。
::

## Movk Nuxt API 系统

Movk Nuxt 为每个端点创建一个包装 ofetch 的 API 客户端（[`$api` 插件](/docs/api/api-plugin)），以及一组封装 `useFetch` 的 composable，在 Nuxt 原生数据获取能力之上提供统一的认证、业务检查、错误归一、Toast 提示等增强功能。

```text
nuxt.config.ts (movk.api 配置)
    |
    v
api.factory.ts 插件 -- 按端点创建并缓存 $api 客户端
    |
    v
端点客户端（每次调用：内置钩子在前、用户钩子在后组合，互不覆盖）
├── onRequest:   认证注入 -> debug 日志 -> movk:api:request hook
├── onResponse:  流内 JSON 还原 -> 业务检查 -> 数据解包 -> movk:api:response hook -> 成功 Toast
└── 出口 catch:  归一为 ApiError -> 401 处理 -> movk:api:error hook -> 错误 Toast（重试结束后只上报一次）
    |
    v
Composables
├── useApiFetch             useFetch + $api (SSR/CSR 通用)
├── useLazyApiFetch         lazy: true 预设
├── useClientApiFetch       server: false, lazy: true 预设
├── useUploadWithProgress   $api 管线 + XHR 适配器上报上传进度
├── useDownloadWithProgress $api.raw 流式读取 + 下载进度
└── useApiStream            $api.stream() + SSE 解析 + 中止
```

上传、下载、流式请求与 `useApiFetch` 走同一条客户端管线，端点请求头、认证、业务检查、错误分类与 hook 完全一致。
流式响应（SSE、二进制）不进业务检查与解包链路：`onResponse` 识别到可读流即整段短路，
由 [`useApiStream`](/docs/api/stream) 或 [`createChatTransport`](/docs/api/stream) 接手。

### 多端点支持

支持配置多个 API 端点，每个端点可独立设置 baseURL、认证、Toast 和响应规则。通过 `endpoint` 选项或 `$api.use()` 切换端点。

::tip{icon="i-lucide-settings" to="/docs/getting-started/configuration#endpoints"}
了解端点配置选项
::

### 自动认证

与 `nuxt-auth-utils` 集成。启用后，每次请求自动从 session 提取 token 并注入到请求头。支持嵌套路径（如 `user.accessToken`）和多种 token 格式（Bearer、Basic、Custom）。

::tip{icon="i-lucide-settings" to="/docs/getting-started/configuration#auth"}
了解认证配置选项
::

### 业务状态码检查

`$api` 拦截器自动检查响应 `code` 是否在 `successCodes` 中，业务失败时抛出 `ApiError` 并显示 Toast。直接返回裸资源的端点可在端点 `response` 上关闭 `businessCheck`。

::tip{icon="i-lucide-arrow-right" to="/docs/api/api-plugin#数据解包与业务校验"}
查看业务校验与 `businessCheck` 的交互示例
::

### 数据解包

`$api` 拦截器自动提取响应中 `dataKey`（默认 `data`）字段，泛型 `T` 直接对应业务数据类型。

::tip{icon="i-lucide-arrow-right" to="/docs/api/api-plugin#数据解包与业务校验"}
查看解包与 `unwrap` 的交互示例
::

### 错误归一

所有失败（业务码、HTTP 4xx/5xx、网络中断、超时）统一为 `ApiError`（`NuxtError<ApiErrorData>`），按 `error.data.kind` 区分场景；`useApiFetch` 的 `error` 与 `$api` 抛出的错误是同一对象。

::tip{icon="i-lucide-arrow-right" to="/docs/api/use-api-fetch#错误分类"}
查看错误分类示例
::

### Toast 提示

请求成功/失败时自动显示 Toast 提示。支持四层配置优先级：请求级 > 端点级 > 全局级 > 内置默认值。可在任意层级禁用或自定义。

::tip{icon="i-lucide-settings" to="/docs/getting-started/configuration#toast"}
了解 Toast 配置选项
::

### 401 未授权处理

收到 HTTP 401 或业务码 401 时（含上传 / 下载进度请求），默认自动清除 session 并跳转登录页。可通过 [API Hooks](/docs/api/hooks#movkapiunauthorized) 拦截并实现自定义逻辑（如 token 刷新）。

::tip{icon="i-lucide-settings" to="/docs/getting-started/configuration#auth"}
了解 401 处理配置选项
::

## 从 v1 迁移到 v2

v2 把响应处理收敛到每个端点一个客户端，以下变更需要调整调用方代码：

| 变更 | v1 | v2 |
| --- | --- | --- |
| 请求级开关改为正向命名 | `skipBusinessCheck: true` / `skipUnwrap: true` | `businessCheck: false` / `unwrap: false` |
| `$api` 请求级选项不再包在 `context` 中 | `$api(url, { context: { toast: false } })` | `$api(url, { toast: false })` |
| 裸资源端点在端点上声明 | 每个请求传两个 skip 开关 | `endpoints.x.response: { businessCheck: false, unwrap: false }` |
| 所有失败统一为 `ApiError`（NuxtError） | `error.isBusinessError`、`error.response`；HTTP / 网络错误为 `FetchError` | `error.data.kind === 'business'`、`error.data.response`；HTTP、网络、超时同样是 `ApiError` |
| `movk:api:error` 新增错误参数，只触发一次 | `(context)`，GET 5xx 重试时触发两次，网络错误不触发 | `(context, error)`，重试结束后触发一次，网络错误与超时同样触发 |
| 上传超时选项改名 | `timeoutMs` | `timeout` |
| 上传 / 下载请求头与 `$api` 同序叠加 | 用户 `headers` 覆盖 auth 头，且忽略端点 `publicHeaders` | 注入端点 `publicHeaders`；启用认证时 auth 头最后写入、优先级最高 |
| 上传 / 下载关闭校验后仍解包 | `skipBusinessCheck` 返回原始响应体 | `businessCheck: false` 仍按 `dataKey` 解包，需要原始响应体时再传 `unwrap: false` |

`$api` 中用户传入的 `onRequest` / `onResponse` 不再覆盖内置拦截器，v1 中依赖覆盖来绕过解包的写法需改为 `unwrap: false`。
