## Introduction

`$api` is a global `$fetch` instance injected by a Nuxt plugin, with a full built-in interceptor chain (auth injection, business status code checking, data unwrapping, Toast notifications). It is the underlying engine for all API composables (`useApiFetch`, `useLazyApiFetch`, etc.).

## Usage

```ts
const { $api } = useNuxtApp()

// GET request (data is automatically unwrapped)
const users = await $api<User[]>('/users')

// POST request
const user = await $api<User>('/users', {
  method: 'POST',
  body: { name: 'test', email: 'test@example.com' }
})

// PUT request
const updated = await $api<User>(`/users/${id}`, {
  method: 'PUT',
  body: { name: 'new-name' }
})

// DELETE request
await $api(`/users/${id}`, { method: 'DELETE' })
```

::note
Data returned by `$api` has already been automatically unwrapped by the interceptor (the `dataKey` field is extracted); the generic `T` directly maps to the business data type.
::

## Multi-Endpoint Switching

Use `$api.use(endpoint)` to switch to a specific endpoint:

```ts
const { $api } = useNuxtApp()

// Use the default endpoint
const users = await $api('/users')

// Switch to the admin endpoint
const adminUsers = await $api.use('admin')('/users')

// Save an endpoint reference to avoid repeated use() calls
const adminApi = $api.use('admin')
const config = await adminApi('/config')
const stats = await adminApi('/stats')
```

Endpoint instances are internally cached, so multiple calls to `$api.use('admin')` return the same instance.

## Auth Integration

When `auth` is enabled and `tokenSource` is `'session'` (default), the module automatically integrates with `nuxt-auth-utils`: after login it reads the token from `session[sessionTokenPath]` and all `$api` requests automatically inject the `Authorization` header. On a 401 response, the `auth.unauthorized` strategy clears the session or redirects to the login page.

## Data Unwrapping and Business Validation

`$api` extracts business data by `response.dataKey` and validates the business code against `successCodes` by default. The `unwrap` / `businessCheck` switches can be declared globally, per endpoint or per request, with precedence explicit request value > endpoint > global. Select a mode in the dropdown to observe the difference in the returned structure:

- `default`: Extracts business data by the default `data` field; the caller receives the de-enveloped object directly.
- `no-unwrap`: `unwrap: false` — does not overwrite `response._data`, preserving the full `code/message/data` envelope.
- `no-business-check`: Legacy endpoints that don't return a `code` field — `businessCheck: false` disables validation and still unwraps the business data by `dataKey`.
- `combined`: Non-standard external envelopes — disable both to let the caller handle the response entirely.

### Endpoint-Level Declaration

Returning a bare array or object (no `{ code, data }` envelope) is an inherent property of an endpoint. Declare it once on the endpoint `response`, and every request to that endpoint (including upload, download and streaming) follows it:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  movk: {
    api: {
      endpoints: {
        sensor: {
          baseURL: process.env.NUXT_SENSOR_URL,
          response: { businessCheck: false, unwrap: false }
        }
      }
    }
  }
})
```

```ts
// Receives the array directly
const points = await $api.use('sensor')<SensorPoint[]>('/point-numbers')

// Explicit request values win: re-enable business-code checking for a single request
await $api.use('sensor')('/legacy', { businessCheck: true })
```

::note
With checking enabled, a non-object response body (`null`, string, array, etc.) is treated as a business failure (`error.data.kind` is `business`) instead of throwing a `TypeError`.
::

## Toast Notifications

`$api` has built-in Toast notifications, determining success/failure by `toast.successCodes`. Supports two levels of customization: global defaults and per-request overrides. Select a mode in the dropdown and toggle the "inject error" switch to observe the success/failure branches:

- `default`: No `toast` passed — inherits global config; both success and error use the default style.
- `silent`: `toast: false` — disables all per-request notifications.
- `message`: `successMessage` / `errorMessage` replace the default text.
- `error-only`: `{ success: false }` — disables success notification but keeps error notification.
- `custom`: Overrides `color`, `icon` and other ToastProps for success and error separately.

::note
Setting `toast.success.methods` in the global or endpoint config limits success notifications to mutating requests (POST / PUT / PATCH / DELETE). A single GET can still opt back in with request-level `{ success: { show: true } }` or `successMessage`.
::

## Using in Event Handlers

Using `$api` inside event handlers is the most common scenario:

```vue
<script setup lang="ts">
const { $api } = useNuxtApp()

// Form submission
async function handleCreate(formData: CreateUserRequest) {
  try {
    const user = await $api<User>('/users', {
      method: 'POST',
      body: formData
    })
    // Toast is shown automatically, no manual handling needed
    navigateTo(`/users/${user.id}`)
  }
  catch (error) {
    // Business error Toast is shown automatically
    // Add extra logic here if needed (e.g. highlight form fields)
  }
}

// Delete confirmation
async function handleDelete(id: string) {
  await $api(`/users/${id}`, { method: 'DELETE' })
  await refreshNuxtData() // Refresh page-cached data
}
</script>
```

## Using in useAsyncData

When you need to aggregate multiple endpoints or do complex data processing, use `$api` inside `useAsyncData`:

```ts
const { $api } = useNuxtApp()

// Aggregate multiple endpoints
const { data: dashboard } = await useAsyncData('dashboard', async () => {
  const [users, stats, recent] = await Promise.all([
    $api<User[]>('/users'),
    $api<Stats>('/stats'),
    $api<Activity[]>('/activity/recent')
  ])
  return { users, stats, recent }
})
```

### Wrapping a Custom Composable

```ts [app/composables/useDashboard.ts]
export function useDashboard() {
  const { $api } = useNuxtApp()

  return useAsyncData('dashboard', async () => {
    const [users, stats] = await Promise.all([
      $api<User[]>('/users'),
      $api<Stats>('/stats')
    ])
    return { users, stats }
  })
}
```

### Business Operation Composable

For write operations such as delete or approve, encapsulate the `$api` calls in a dedicated composable to keep page files lean:

```ts [app/composables/useUserActions.ts]
export function useUserActions() {
  const { $api } = useNuxtApp()

  async function remove(id: string) {
    await $api(`/users/${id}`, { method: 'DELETE' })
    await refreshNuxtData()
  }

  async function create(data: CreateUserRequest) {
    return await $api<User>('/users', {
      method: 'POST',
      body: data,
    })
  }

  async function updateRole(id: string, role: UserRole) {
    return await $api<User>(`/users/${id}/role`, {
      method: 'PUT',
      body: { role },
      toast: { successMessage: 'Role updated' },
    })
  }

  return { remove, create, updateRole }
}
```

```vue [app/pages/users/index.vue]
<script setup lang="ts">
// Data fetching with useApiFetch
const { data: users, refresh } = await useApiFetch<User[]>('/users')

// Write operations with $api composable
const { remove, updateRole } = useUserActions()
</script>
```

## Per-Request Configuration

Per-request options sit at the same level as ofetch options; `$api`, `useApiFetch`, upload/download and streaming requests share the same shape:

```ts
const { $api } = useNuxtApp()

// Disable Toast
await $api('/users', { toast: false })

// Custom Toast message
await $api('/users', {
  method: 'POST',
  body: formData,
  toast: { successMessage: 'Created successfully' }
})

// Disable business status code checking (still unwraps by dataKey)
const data = await $api('/external-api/data', { businessCheck: false })
```

User-provided hooks such as `onRequest` / `onResponse` run together with the built-in interceptors (built-in first) and never override auth, business validation, unwrapping or Toast:

```ts
await $api('/users', {
  onResponse({ response }) {
    // response._data is already processed by the policy
  }
})
```

::note
These options are declared through a type extension of ofetch's `FetchOptions` and are only recognized by Movk Nuxt's `$api` client; the native `$fetch` ignores them.
::

## Error Handling

Every error thrown by `$api` is an `ApiError` (`NuxtError<ApiErrorData>`), classified by `error.data.kind` as `business`, `http`, `network`, `timeout` or `aborted`. The error Toast and `movk:api:error` fire only once after ofetch retries finish; aborts are not reported:

```ts
try {
  await $api('/orders', { method: 'POST', body })
}
catch (error) {
  const { kind, code } = (error as ApiError).data ?? {}
  if (kind === 'business' && code === 40001) {
    // business-code branch
  }
}
```

## API

### ApiInstance

Type definition of `$api`:

```ts
type ApiInstance = $Fetch & {
  use: (endpoint: string) => ApiInstance
  stream: <T>(url: string, options?: ApiStreamOptions<T>) => Promise<AsyncGenerator<T>>
}
```

::field-group
  ::field{name="$api(url, options)" type="Promise<T>"}
  Send an API request. Supports all ofetch options plus the fields of `ApiRequestOptions`. `$api.raw` returns the full response through the same pipeline.
  ::

  ::field{name="$api.use(endpoint)" type="ApiInstance"}
  Switch to the specified endpoint and return that endpoint's `$api` instance. `endpoint` is typed as `MovkApiEndpointName` (a literal union merged by the module from the `movk.api.endpoints` declaration). Endpoint instances are internally cached; multiple calls return the same instance.
  ::
::

### ApiRequestOptions

Per-request configuration passed alongside ofetch options:

::field-group
  ::field{name="toast" type="RequestToastOptions | false"}
  Toast configuration. Set to `false` to disable all Toast notifications; `{ success: { show: true } }` re-enables it for one request when globally disabled.
  ::

  ::field{name="businessCheck" type="boolean"}
  Whether to validate the business status code against `successCodes`. Inherits the endpoint / global `response.businessCheck` when omitted; when `false`, no business `ApiError` is thrown but the `dataKey` field is still unwrapped.
  ::

  ::field{name="unwrap" type="boolean"}
  Whether to unwrap by `dataKey`. Inherits the endpoint / global `response.unwrap` when omitted; when `false`, the interceptor does not overwrite `response._data` and the caller receives the raw body. Orthogonal to `businessCheck`.
  ::
::

### ApiError

```ts
type ApiError = NuxtError<ApiErrorData>

interface ApiErrorData {
  kind: 'business' | 'http' | 'network' | 'timeout' | 'aborted'
  endpoint: string
  code?: number | string
  response?: unknown
}
```

::field-group
  ::field{name="statusCode" type="number"}
  The HTTP status on HTTP failures; on business failures the business code when it falls within 100–599, otherwise `500`.
  ::

  ::field{name="message" type="string"}
  Error message, preferring the `messageKey` field of the response body.
  ::

  ::field{name="data.kind" type="ApiErrorKind"}
  Error category: `business` failed business-code check, `http` HTTP 4xx/5xx, `network` no response received, `timeout` timed out, `aborted` aborted by the caller.
  ::

  ::field{name="data.code" type="number | string"}
  The original business code (`business`) or HTTP status (`http`).
  ::

  ::field{name="data.response" type="unknown"}
  The raw response body.
  ::
::
