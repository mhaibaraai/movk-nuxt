## When to Use It

Admin APIs often return a shared envelope (`{ code, message, data }`), require an authentication token, and need consistent success and error messages. The API layer handles these concerns in each endpoint client so pages can work with business data:

- Fetch page data, such as lists and details, with the [`useApiFetch`](/en/docs/api/use-api-fetch) family, a thin wrapper around Nuxt `useFetch`.
- Submit or delete data imperatively with [`$api`](/en/docs/api/api-plugin).
- Transfer files with progress using [`useUploadWithProgress` / `useDownloadWithProgress`](/en/docs/api/upload-download).
- Consume SSE or integrate AI chat with [`useApiStream` / `createChatTransport`](/en/docs/api/stream).

These tools share the same request pipeline, endpoint configuration, authentication, business-code checks, error model and [Hooks](/en/docs/api/hooks).

::warning
The API layer depends on the Nuxt server runtime and plugin system and is **available only in Nuxt mode**. Plain Vue + Vite projects using `@movk/nuxt/vite` do not receive `$api`, `useApiFetch*`, uploads, downloads or streaming requests.
::

## Minimal Example

The API layer is enabled by default. The `default` endpoint uses `/api` as its `baseURL`. Override it in `nuxt.config.ts` as needed:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@movk/nuxt'],
  movk: {
    api: {
      endpoints: {
        default: { baseURL: '/api' }
      }
    }
  }
})
```

When the backend returns `{ code: 200, message: 'ok', data: { id: 1, name: 'Alice' } }`, the generic `T` describes the `data` payload directly:

```vue
<script setup lang="ts">
interface User {
  id: number
  name: string
}

const { data, status, error } = await useApiFetch<User>('/user')
// data.value => { id: 1, name: 'Alice' }
</script>
```

## Choose a Tool

| Scenario | Tool | Behavior |
| --- | --- | --- |
| Essential initial page data | `useApiFetch` | Fetches during SSR and blocks client navigation until data is ready |
| Secondary or deferred page data | `useLazyApiFetch` | Fetches during SSR without blocking client navigation |
| Data without SEO requirements | `useClientApiFetch` | Skips SSR and automatically fetches after client hydration |
| Event handlers and aggregated requests | `$api` | Imperative calls returning unwrapped data |
| Uploads / downloads with progress | `useUploadWithProgress` / `useDownloadWithProgress` | Client only; supports cancellation |
| SSE and AI chat | `useApiStream` / `createChatTransport` | Client only; supports cancellation |

`useApiFetch` inherits Nuxt `useFetch` options such as `server`, `lazy` and `immediate` with the same semantics. See [Nuxt data fetching](https://nuxt.com/docs/4.x/getting-started/data-fetching).

## Request Pipeline

The `api.factory` plugin wraps ofetch in one client per endpoint and caches each client by name. Built-in hooks run before user hooks on every call; user-provided `onRequest` / `onResponse` handlers do not replace the built-in logic:

```text
movk.api configuration (merged global + endpoint settings)
    |
    v
Endpoint client
├── onRequest   Inject auth header -> debug log -> movk:api:request
├── onResponse  Restore streamed JSON -> business-code check -> unwrap -> movk:api:response -> success Toast
└── Exit        Normalize to ApiError -> handle 401 -> movk:api:error -> error Toast (reported once after retries)
    |
    v
$api / useApiFetch family / upload (XHR adapter) / download ($api.raw) / streaming ($api.stream)
```

Core rules:

- **Business-code checks**: throws a business error when the response `code` is not in `successCodes`, which defaults to `[200, 0, '200', '0']`.
- **Unwrapping**: extracts business data using `dataKey` (default `data`). The generic `T` describes this payload.
- **Endpoint policies**: disable `businessCheck` / `unwrap` in the endpoint's `response` settings for endpoints returning bare arrays or objects. See [response policies](/en/docs/api/api-plugin#response-policies).
- **Unified errors**: business failures, HTTP 4xx/5xx responses, network failures and timeouts become `ApiError`, distinguished by `error.data.kind`. See [error model](/en/docs/api/api-plugin#error-model).
- **401 handling**: an HTTP 401 or business code 401 clears the session and redirects to the login page by default. Override it with [`movk:api:unauthorized`](/en/docs/api/hooks#movkapiunauthorized).
- **Stream bypass**: SSE and binary responses bypass business-code checks and unwrapping and are consumed by download or streaming tools. An `application/json` response is restored to an object before validation even when read as a stream.

See [Configuration — API](/en/docs/getting-started/configuration#api) for all settings.

## Upgrading from v1

v2 centralizes response handling in one client per endpoint. Update the following patterns:

| Change | v1 | v2 |
| --- | --- | --- |
| Request switches use positive names | `skipBusinessCheck: true` / `skipUnwrap: true` | `businessCheck: false` / `unwrap: false` |
| `$api` request options no longer nest under `context` | `$api(url, { context: { toast: false } })` | `$api(url, { toast: false })` |
| Declare bare-resource policies on the endpoint | Pass both skip switches on every request | `endpoints.x.response: { businessCheck: false, unwrap: false }` |
| All failures use `ApiError` | `error.isBusinessError`, `error.response`; HTTP / network errors use `FetchError` | `error.data.kind`, `error.data.response`; HTTP, network and timeout errors also use `ApiError` |
| `movk:api:error` signature and frequency | `(context)`; twice for GET 5xx retries, never for network errors | `(context, error)`; once after retries, including network errors and timeouts |
| Upload timeout option renamed | `timeoutMs` | `timeout` |
| Upload / download headers | User `headers` override auth; endpoint `publicHeaders` ignored | Endpoint `publicHeaders` are injected; when auth is enabled, its header is written last and takes precedence |
| Upload / download results when checks are disabled | `skipBusinessCheck` returns the original response body | `businessCheck: false` still unwraps with `dataKey`; also set `unwrap: false` for the original response body |

If v1 code bypassed unwrapping by replacing the built-in interceptor with a user `onResponse` handler, use `unwrap: false` instead.
